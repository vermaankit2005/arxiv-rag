# Roadmap

A *likely* order, not a plan. Only the current sprint is real; everything below
it is a guess that later sprints are allowed to overturn.

Each entry names the component and the question it answers. It becomes a sprint
only when the previous sprint ends and we agree it is the next best thing.

| # | Component | The question it answers | Status |
|---|-----------|------------------------|--------|
| 1 | **Loading docs** | can we turn a PDF into text good enough to cite from? | **current** |
| 2 | Chunking | what is the right unit of evidence? | next, probably |
| 3 | Retrieval | can we find the right passage for a question? | later |
| 4 | Grounded answer + citation validation | is the answer honest? *(the product claim)* | later |
| 5 | Scope + evidence gate | does it refuse well? | later |
| 6 | The graph | have the branches outgrown `if/else`? | later |
| 7 | Corpus scale | what breaks at 50 papers? at 500? | later |
| 8 | Interface | can someone who is not us use it? | later |
| 9 | Defensibility | can we explain every decision in two minutes? | later |

## Where the principles land

See `PRINCIPLES.md`. Nothing is scheduled — each principle attaches to the
sprint that first needs it.

## Rule

If we reach a component and cannot name something currently broken that it
fixes, we skip it and write down that we skipped it. Skipped components are as
much a result as built ones.
